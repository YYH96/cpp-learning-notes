# 역할 분리

## 개념과 동작 원리

객체와 모듈마다 어떤 데이터와 변경 규칙을 책임지는지 정합니다. 협력하는 객체는 필요한 인터페이스로 연결하고 다른 객체의 내부 상태에 과도하게 의존하지 않습니다.

## 사용 시점과 다른 개념의 구분

보드는 칸·판정, 플레이어는 개인 상태·행동, 관리자는 전체 진행을 맡도록 나눕니다. 클래스 수를 늘리는 것 자체가 목표는 아닙니다.

## 문법과 예제

| 역할 | 책임 | 예 |
| --- | --- | --- |
| 보드 | 칸·좌표·보드 판정 | 빙고, 틱택토 |
| 플레이어 | 개인 상태·행동 | 체력, 이동, 선택 |
| 게임 관리자 | 시작·반복·종료 조율 | 게임 루프 |
| 씬 | 화면별 동작 제공 | 로비, 게임, 전투 |

**핵심:** 한 객체에 입력·규칙·화면·메모리 관리가 모두 몰리지 않도록 역할을 나눕니다.

## 예제를 이해하는 순서

관리자는 보드 판정 함수를 호출하지만 판정 내부 반복문까지 직접 관리하지 않습니다. 같은 규칙이 여러 역할에 중복되면 수정 누락이 생길 수 있습니다.

## 이해 확인

**질문:** 모든 기능을 서로 다른 클래스에 넣으면 좋은가?

**답:** 함께 바뀌는 책임은 묶고 독립적으로 바뀌는 책임은 분리하는 기준이 필요합니다.
